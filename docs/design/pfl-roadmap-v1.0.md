# pfl v1.0 Roadmap

## 1. Context and Goals

With the completion of v0.1, the `pfl` (Pre-Flight Listen) tool has established its foundation for discovering and resolving coding-agent harnesses. The v1.0 milestone focuses on four strategic pillars, with security as the absolute priority:

1. **Security Hardening (Primary)**: Protecting against hostile repositories and aligning with the rigorous security standards of the `yuurei` project.
2. **Harness Depth**: Deepening the parsing capabilities for existing runtimes (Claude Code, Codex).
3. **Machine-Readable Interfaces**: Fulfilling the prerequisite conditions for future Analyzer integration.
4. **Third Runtime Support**: Introducing the OpenCode adapter.

**Platform Target**: POSIX (macOS / Linux) only.
**Public Contract**: CLI and on-disk schema only (no public library API).

## 2. Scope Matrix

The v1.0 roadmap addresses items deferred in the v0.1 design document (`docs/design/pfl-design-v0.1.md`), decisively promoting or continuing to defer them.

### Promoted to v1.0
* **Snapshot retention / GC**: Necessary to prevent infinite storage growth.
* **Export format policy**: Transitioning `--json` to output valid documents for programmatic consumption.
* **Additional runtimes**: Introduction of the OpenCode adapter.
* **M5 Prerequisites**: Headless execution, single-document export, and on-disk schema freezing.

### Deferred (v1.0 Non-Goals)
* **Advanced semantic graph analysis (M4b)**: Overlaps with natural language semantic inference.
* **Analyzer integration (M5 Body)**: Deferred until `yuurei` integration requires it.
* **Optional LLM enrichment**: Maintains the deterministic, LLM-free core design.
* **Project aliases**: Not critical for the v1.0 value proposition.
* **Windows support**: Explicitly scoped out in favor of POSIX focus.

## 3. Security Baseline and Findings

Because `pfl` inherently reads untrusted harness files from cloned repositories, security is central.

### 3.1. Successfully Maintained Invariants

The v0.1 implementation correctly enforces several critical security boundaries. These must be preserved:

| Invariant | Evidence / Implementation |
|---|---|
| **No execution** | Zero usage of `child_process`, `exec`, `spawn`, `eval`, `vm`, or dynamic `import()`. |
| **No runtime activation** | Version detection parses filenames/JSON without executing binaries. |
| **Uses `lstat`** | Exclusive use of `lstat` over `stat` for file discovery. |
| **Path confinement** | Lexical `..` escape blocking; `realpath` bounds checking against the project root. |
| **Minimal content-derived paths** | Almost zero resolution of paths sourced from untrusted file content. |
| **Traversal prevention** | Project IDs are hashed, avoiding attacker-controlled bytes in paths. |
| **Prototype pollution defense** | `Object.create(null)` used; no deep merges of settings objects. |
| **Atomic write / Immutable store** | `writeArtifact` uses temp-to-`link()` with `EEXIST` rejection. Re-asserts `0o700`/`0o600`. |
| **Redaction separation** | Digests are computed on raw bytes; redaction operates independently on metadata. |

*Note: While `ObservedSnapshot` uses `deepFreeze`, `ResolvedSnapshot` currently does not. This asymmetry will be addressed.*

S9 through S12 are low-severity residuals, each dispositioned individually in M6.

### 3.3. Security Operations (Yuurei Level)

To achieve parity with `yuurei`, the following 5-layer security apparatus will be implemented:

1. **CI Scans**:
   * `semgrep` for immediate pattern feedback on all PRs.
   * `codeql` (security-extended) on PRs and nightly.
   * `gitleaks` for differential and historical secret detection.
   * `dependabot` for weekly dependency updates.
2. **Review Layers**:
   * A dedicated `security-auditor` agent rewritten explicitly for `pfl`'s 12 design invariants.
   * Mandatory `/security-review` before merging any PR touching trust boundaries, enforced by a **required status check on the protected branch**, so a pull request touching those paths cannot merge until the review has run. The check runs on every pull request and decides for itself whether the diff touches a trust boundary, reporting success immediately when it does not. Selecting it by path filter was rejected: a required check that a path filter can skip is absent exactly when a file outside the filter turns out to matter. A documented convention was considered and rejected: a solo-maintained repository is exactly where a convention is easiest to skip.
3. **Trigger Points**: Explicit boundaries requiring review include `walk.ts`, `util/fs.ts`, `consent.ts`, `redact/**`, `store.ts`, `project-identity.ts`, `paths.ts`, and `metadata.ts`.
4. **Record Keeping**: A `docs/security/` registry including `review-policy.md`, formal accepted risks, and release-candidate audit logs that track prior findings across audits.
5. **SECURITY.md**: Documenting the private disclosure flow and SLA (3-day acknowledgement).

## 4. Functional Gaps

Two major functional deficiencies contradict the v0.1 design principles:

1. **Absence of a Frontmatter Parser (Principle #2: Resolution over listing)**:
   Currently, elements like skills and subagents are only listed by path and digest. Their metadata (names, descriptions, tools) is not extracted. Implementing a frontmatter parser is required to transition from mere listing to actual resolution.
2. **Impossibility of Headless Execution (Principle #8: Composable with higher layers)**:
   Running `pfl inspect --json` throws an error due to the lack of interactive consent, with no CLI flags to bypass or inject consent. This structurally prevents CI automation and programmatic composition.

## 5. Milestones

This document fixes what v1.0 sets out to do, the decisions that must hold across
milestones, and the conditions each milestone closes on. It deliberately stops short of
detailed design. Comparison keys for sorting relations, the behaviour of `--keep 0`,
recovery from a corrupted root index, locking for a concurrent first run, and the numeric
values behind the resource limits are all settled in the design work and ADRs that each
milestone opens with — not here. Where this document says a contract is frozen, the
freeze is the milestone's deliverable; the wire-level detail belongs to the issue that
delivers it.

The execution of v1.0 is organized into sequential milestones. The dependencies between them are intentional, and two of them constrain the ordering more tightly than the numbering suggests:

* **Consent must become a choke point (M8) before a new adapter is added (M9).** Consent is presently enforced by each adapter remembering to check it; the walk and path layers have no notion of it. Until that is inverted, a new adapter's safety rests on review rather than on construction.
* **The OpenCode scope and origin investigation runs before the M8 freeze, even though the adapter itself is built in M9.** M8 freezes the on-disk schema and `ElementId`; if OpenCode turns out to need an origin or scope the frozen schema cannot express, the freeze would have to be reopened. Splitting the investigation from the implementation keeps the freeze final.

The resulting order of work is: investigate OpenCode's scope and path model → inventory every read path → settle the consent choke point and the schema's extensibility → freeze → extract the shared adapter scaffold → implement the adapter → security review and hostile fixtures.

### M6: Security Hardening (Highest Priority)
* **Goal**: Resolve every finding in §3.2 — by remediation where a fix exists, or by a recorded accepted risk where one does not — and establish the security operations baseline.
* **Acceptance Criteria**:
  * S1 fixed via correct branching order and `lstat` guards.
  * S3 fixed by skipping nodes with `nlink > 1`.
  * **Every filesystem read path inventoried.** This is a prerequisite for S2 rather than a separate concern: consent wording cannot be derived from the code until the set of reads is known. The inventory covers every read path in the shipped code — the adapter path tables, `project-identity.ts`, the detection paths, and the snapshot store — and each later adapter extends it as part of its own security review. M8 consumes this inventory to place the consent choke point.
  * S2/S4 fixed by deriving consent wording from the inventory above, so the prompt cannot silently fall behind the code. The `✗ Follow symlinks` line becomes true once S1 is fixed, and the test that pins the current inaccurate string is updated with it.
  * **S6/S8 fixed across every channel that leaves the process, not only the two named in the finding.** Persisted: `source.path`, `diagnostics` (both `message` and `path`, including the raw `Error.message` embedded by the store), `project.root`, and `project.remote`. Displayed: `show`, `report`, `list`, `graph`, `diff`, and `snapshots`, all of which currently print diagnostics unredacted, and `show --json`, which prints whole elements. The `display` / `export` / `persistence` tiers in `redact/common.ts` are wired to actual call sites; they are presently defined and unused, which is why display is a strict superset of persistence. Closed by a property test — every field that is persisted or displayed passes through the allowlist, the redaction layer, or both — rather than by enumerating call sites once. The two project fields need a stated basis rather than an exemption: `project.root` is persisted with the home prefix replaced by `~`, so it carries a path shape without the account name, and `project.remote` passes the URL-credential rule. Both are declared in the schema with that treatment, so the property test has something to assert against.
  * **S7 fixed by limits whose targets and semantics are fixed here; the numeric values are set during implementation.** The limited quantities are: bytes read per file, total entries walked, directory recursion depth, snapshot artifact read size, and JSON/TOML parse input size. Non-regular files — FIFOs, sockets, devices — are never opened; they are identified from the `lstat` mode already fetched and recorded as skipped, which also removes the indefinite hang a FIFO currently causes. Exceeding a limit marks that element `skipped` with a stable diagnostic code and sets `completeness: "partial"`; it never aborts the run, so the best-effort invariant continues to hold. The limits are named constants in v1.0, not user-configurable, keeping them out of the frozen CLI contract; making them configurable is a later decision. The initial values are not left to implementation taste: they are proposed and recorded as an input to this milestone's security review, since a DoS ceiling nobody reviewed is not a ceiling anyone can vouch for. Two further consequences are part of the criterion: the tests reference those same constants rather than restating numbers, so a limit cannot be changed without the hostile-input corpus moving with it, and changing one requires a security review under §3.3. The diagnostic emitted on exceeding a limit names which limit was hit and its value, so a user who meets one in a large but legitimate repository can see why an element was skipped rather than only that it was.
  * **S5 resolved by not reading external `.git` references before consent.** The reads are content-derived, unconfined, and occur inside `resolveProjectContext` *before* consent is resolved, on every command — a hop limit would cap runaway traversal without addressing that. **Decision: when `.git` is a file, its `gitdir:` target is not followed until consent has been resolved.** No invariant is weakened, and nothing is entered in the accepted-risk register for S5.
    The cost is that a linked worktree has no git-derived identity on a first, unconsented run, so `projectId` falls back to the canonical path. The milestone therefore also fixes the transition: a project whose identity later resolves to a git remote must not strand the snapshots written under its path-derived id. This is the same reclamation problem M8 addresses for remote changes, and the two are solved together.
  * **S9 through S12 dispositioned individually**, not left as a choice:
    * **S9 (TOCTOU between check and read) — accepted risk.** Exploitation requires a local attacker winning a sub-millisecond race, and the payoff is a digest and a byte count, since content is not persisted for walked files. The one place where the race mattered — the settings read that had no check to race — is removed by the S1 fix. Recorded in the register with this reasoning.
    * **S10 (`permissions.json` weaker than the store) — fixed, with one accepted residual.** The `chmod` re-assertion and the `try`/`finally` temp-file cleanup that `store.ts` already performs are applied to the consent writer. Coarse granularity is addressed by the scope taxonomy in M8. That the file is tamperable by anything running as the same user is an **accepted risk**: a same-uid process can read the harness directly, so integrity protection here would not raise the bar.
    * **S11 (shallow observed-snapshot validation) — fixed.** `isObservedSnapshot` validates element contents the way `isResolvedSnapshot` already validates resolved ones, and the artifact read is subject to the size limit introduced for S7.
    * **S12 (`isPathWithin` separator and case assumptions) — fixed.** The separator is taken from the path module rather than hardcoded. Case is the harder half, and "use platform semantics" would not settle it: Node's path handling does not report whether the underlying volume is case-insensitive, which is a property of the filesystem and not of the platform. The comparison therefore relies on the realpath results the OS returns for both sides, and the case-insensitive behaviour is verified on a case-insensitive volume — the macOS runner added in M10 — rather than asserted. POSIX-only support is documented in M10; this fix is about correctness on a supported platform, not about Windows.
  * Hostile input corpus added to the test suite: large files, deep trees, FIFOs, hardlinks, symlinks pointing at settings files, `.git` files carrying a traversing `gitdir:`, pathological TOML lines, and corrupted snapshots.
  * **Test credibility gaps closed.** The present suite passes while leaving the channels that matter unchecked:
    * The persistence test reads store artifacts through a helper that swallows read errors into empty strings, so it passes vacuously when the store is empty or `HOME` is misdirected. A positive control asserting the artifacts are non-empty is added.
    * The read-only test fingerprints the project root only, never the user scope that is read under consent, and its fingerprint covers content and mtime but not file mode. Both are extended.
    * The no-execution guard greps five patterns and misses `eval`, `new Function`, `vm`, dynamic `import()`, and `require(`. The pattern set is widened.
    * Consent and end-to-end coverage exist for Claude Code only; Codex equivalents are added.
  * Each security invariant test is falsifiable: reverting the corresponding fix turns the suite red. This is the property the existing symlink test lacks, since its fixture exercises only the one path that already behaved correctly.
  * Yuurei-level CI scans, `SECURITY.md`, and audit tracking established.

### M7: Harness Depth
* **Goal**: Fulfill the "Resolution over listing" principle for the existing adapters. Today the most numerous element kinds are recorded as a path, a digest, a size, and a format, which is listing rather than resolution.
* **Acceptance Criteria**:
  * Frontmatter parser implemented as a shared module and used for skills, subagents, commands, rules, output styles, and memory files. Only structural metadata — declared key names, tool names, lengths — is extracted and persisted through the existing allowlist; raw instruction text is still never persisted, so deny-by-default is unaffected.
  * Claude Code: managed scope discovered, emitting the `managed` origin that `NativeOrigin` already declares but that no adapter currently produces.
  * Claude Code: `.mcp.json` server names enumerated, removing the asymmetry in which the two other MCP sources are parsed while the canonical project file is only digested.
  * Claude Code: approval-policy detection corrected. The element keys on a top-level `defaultMode`, while the runtime writes `permissions.defaultMode`, so the branch rarely materialises.
  * Claude Code: `plugin` elements resolved and classified. They currently fall through to `unknown` on all four resolution axes and carry no facets.
  * Claude Code: hooks resolved beyond top-level event names, recording matcher patterns and per-event structure. Command strings remain unpersisted.
  * Claude Code: `CLAUDE.md` discovery extended to parent and nested directories, and the shadowing relation between `CLAUDE.md` and `CLAUDE.local.md` computed.
  * Codex: the discovery surface corrected against the runtime's actual layout, which differs from what the adapter assumes. `~/.codex/agents/` — the source of the `custom-agents` kind — **does not exist**, while `config.toml` carries `[projects.*]`, `[hooks.state]`, `[marketplaces.*]`, `[plugins.*]`, `[shell_environment_policy]`, and `[sandbox_workspace_write]`, none of which the adapter reads. `[projects.*]` in particular contradicts the note in `codex/paths.ts` that Codex has no project-scoped configuration: it has it, stored centrally rather than in the project. Each section is either modelled or recorded as a known-unsupported area, and the source comments asserting the layout are replaced by fixtures.
  * Codex: kind assignments corrected. `rules/**` is instructional content, not `permissions`; `model`, `model_reasoning_effort`, and `service_tier` are not compaction controls. The actual context controls (`model_context_window`, `model_auto_compact_token_limit`) are read instead.
  * Codex: the two dead kinds decided rather than left open. **`skill-dependencies` is implemented as frontmatter-derived metadata on the existing `skills` kind** — declared dependency names carried through the allowlist — rather than as an element kind of its own, since a dependency is a property of a skill and not a separately discoverable file. **`multi-agent-configuration` is withdrawn for the versions this adapter verifies**, along with its unreachable classifier row: no directory or configuration section behind it was found in the layout of the verified range. The limits of that evidence are stated rather than glossed. It is a single observed installation, so it supports "not present in the verified range", not "does not exist". And withdrawal is not self-correcting: an unknown item is recorded as `unsupported-by-adapter` only inside an area the adapter actually searches, so a kind whose directory is no longer searched would simply not be found. A trigger is therefore required that can detect something the adapter does not look at, which a fixture cannot: fixtures only cover searched areas, so a kind reappearing in an unsearched directory would leave them green. The trigger is a **layout reconciliation performed whenever the verified range moves** — the adapter's searched areas are compared against the runtime's actual configuration surface for that version, and the difference is recorded in the adapter's documented scope. Withdrawn kinds are re-checked as part of that reconciliation.
  * Codex: project-scoped skills discovered, and `AGENTS.md` discovery extended up and down the directory tree. This also makes `overrideShadowing` reachable; it is presently dead code, because only one directory is ever examined.
  * Codex: `fallback-instructions` classified. `AGENTS.override.md` is the runtime's highest-precedence instruction file and currently resolves to zero facets with unknown confidence.
  * Codex: TOML parser expanded beyond top-level double-quoted scalars, covering `[profiles.<name>]`, `[sandbox_workspace_write]`, `writable_roots`, `network_access`, and non-string scalar types.
  * Runtime version handling made substantive: resolution branches on the detected version wherever semantics differ, rather than the verified range producing only a warning label. Detection also covers installs that are not installer-managed — npm global, Homebrew, PATH-only — which today yield `version: null` and an unverified warning on a supported release.
  * `installed` gains an `unknown` state, so "not consented" is distinguishable from "not installed".
  * Verified-range claims backed by fixtures, so a runtime layout change fails a test instead of silently invalidating a source comment.
  * Classification and findings gaps closed: `subtree-specific-instruction` becomes able to fire, since neither adapter currently returns `directory-subtree` applicability, and `broad-tool-access` fires for Codex once the `permissions` kind carries real permission data. The declared `low` classification confidence is **removed from the type**: no table row emits it, and the scale the classifier actually expresses is high, medium, and unknown. Removing it is preferable to inventing a rule that would emit it, because the confidence values are part of the interpretation schema being frozen.

### M8: Machine-Readable Interfaces and Schema Freeze
* **Goal**: Solidify the programmatic interface and freeze it. Because v1.0 freezes both the on-disk schema and the element identity scheme, every open question about their shape has to be settled inside this milestone: after the freeze, changing either one invalidates the diff history of every stored snapshot.
* **Acceptance Criteria — decisions frozen in this milestone.** These fix the shape of the public contract. Each is settled here, before anything downstream is built against it; reopening one after the freeze invalidates stored snapshots or published output.
  * **The OpenCode scope, origin, and path model investigated and documented — as work belonging to this milestone, not borrowed from M9.** A runtime whose scope model does not fit `project | user | managed | plugin | builtin` would force a schema change *after* the freeze. The freeze either accommodates the model found, or records that OpenCode requires no new origin. M9 implements the adapter against whatever is frozen here and does not alter it.
  * **Headless consent specified as part of the frozen CLI contract.** **Decision: a repeatable `--allow-scope <runtime>:<scope>` flag, matching the key format `~/.pfl/permissions.json` already uses.** No blanket grant such as `--yes` is provided: a CI job names what it permits, so widening the set of locations `pfl` reads in a later version cannot silently widen an existing job's grant. The flag grants for the current run and does not write the consent store, keeping automated runs from mutating a developer's saved grants. The scope names are fixed here, since a narrow grant means nothing without them: **`<runtime>:user`** covers that runtime's user harness, and **`<runtime>:install`** covers its installation and version metadata, which a caller may reasonably refuse while still inspecting the harness. External `.git` references are not a scope, because under the S5 decision they are not read before consent at all. Each scope is backed by the subset of the M6 inventory it authorises, and that correspondence is asserted by the same test that keeps the consent prompt aligned with the code.
    Splitting the scope means splitting the request that carries it: `getConsentRequest` returns one request per scope instead of the single `scope: 'user'` it hardcodes today, the prompt lists the two groups separately and accepts a per-group answer, and each grant is independent. The partial outcomes are defined rather than left to fall out of the code. Granted `install` but not `user`: the user harness is not discovered, and its absence is recorded as a diagnostic rather than presented as an empty harness. Granted `user` but not `install`: discovery proceeds and version detection yields the `unknown` state introduced in M7, which downgrades resolution confidence and raises the compatibility warning — the behaviour that already exists for an unrecognised install. Project-local discovery stays implicit and needs no flag. A run that still lacks a required grant exits 5 and, under `--json`, emits the missing scope keys in the document rather than only in prose, so a caller can act on it.
  * **`--json` defined as a contract, and the contract written out rather than described.** It covers every command that produces output — the seven from v0.1 plus `gc`, introduced below — so the envelope and its golden files have a fixed, enumerable scope. The terms frozen for v1.0:
    * **One document per run.** stdout carries exactly one JSON object and nothing else; every log line, progress message, and human-readable warning goes to stderr. This is what the present implementation violates, by emitting each store diagnostic as its own stdout line before the payload.
    * **A common envelope**: `pflVersion`, `command`, `ok`, `completeness`, `diagnostics`, and `data`. Only `data` varies by command; a reader can parse the envelope without knowing which command produced it. `ok` and `completeness` answer different questions and are not redundant: `ok` is true whenever the command did its job, partial results included, and false only when something stopped it, which is exactly when the exit code is non-zero. `completeness` describes the harness that was observed. A run that skipped every element against a limit is `ok: true` with `completeness: "partial"`; a run that failed to read the store is `ok: false`.
    * **`diagnostics`** uses the same shape as the persisted form — `severity`, `code`, `message`, and optional `path` — so a consumer reads one schema whether it comes from the document or from a stored snapshot. Codes are stable identifiers; messages are not.
    * **Partial results do not get their own exit code.** A run that reaches `completeness: "partial"` exits 0, because best-effort completion is normal operation for this tool — an unreadable file in a user's harness is not a failure of the run. Callers that need to react check `completeness`. Exit codes are otherwise unchanged from v0.1 (2 config, 3 unsupported runtime, 4 inspection failed, 5 consent required, 6 store failure), and the frozen set gains no new members.
    * **Every exit emits the envelope, including failures.** A non-zero exit sets `ok: false` and puts `{ "error": { "code", "message" } }` in `data`, where `code` is the stable name of the exit code rather than its number. This closes the contract over the paths that currently print a bare message and nothing else — unknown runtime, configuration error, inspection failure, and store failure — and it is why `withErrorHandling` in `src/index.ts` changes: under `--json` it emits the envelope instead of calling `logger.error` alone. Consent absence is the same shape, exiting 5 with the missing scope keys in `data`, so a caller acts on the document rather than parsing prose from stderr.
    * **Unknown fields are ignored by readers.** Adding a field is a minor change; removing one, renaming it, or changing its type is a major change. This governs the CLI document only. The on-disk artifacts are a separate contract with a stricter rule — any change to the persisted shape bumps `SNAPSHOT_SCHEMA_VERSION`, including an addition — and the two are deliberately not unified: a reader of a stored snapshot must not guess, whereas a consumer of command output should tolerate a newer `pfl`. Array order is part of the contract only where stated: elements are ordered by id, diagnostics in emission order.
    * **`diff --json`** regains `observedSnapshotIdA` and `observedSnapshotIdB`, which it computes today and omits, and adds a relations diff as added and removed arrays of `{type, from, to}`, sorted the way elements are.
    Findings are diffed too. An earlier draft excluded them, on the grounds that a findings delta computed from different classifier versions would report classifier changes as harness changes — but that argument applies equally to `facetDeltas`, which the design document requires as one of the three diff levels and which is computed from the same classifier output. Excluding one and keeping the other answered the objection in half. The consistent treatment is to diff both and to name the hazard where it occurs: when the two sides' interpretations came from different `CLASSIFIER_VERSION`s, the diff says so, exactly as it already reports differing runtime and resolution-semantics versions.

  * **`ElementId` derivation settled before the freeze.** ADR 0001 recorded that deriving identity from runtime + origin + path alone collides when one file yields several elements, and left the question open. Collisions are avoided today only by an unenforced naming convention (synthetic fragment paths such as `settings.json#permissions`) that three modules parse independently. Either extend the derivation or make the convention type-enforced, and record the outcome in a new ADR.
  * **Schema-version failure handling reconciled with ADR 0001.** Read paths currently diverge: `listRuns` degrades to a diagnostic as the ADR requires, while `readArtifact` converts the same condition into exit 6. Unify them so the first schema bump does not make every read command fail on older binaries.
  * **Project identity resolved by a root index, so history is never stranded.** Adding, changing, or removing a git remote currently mints a new project id and abandons the snapshots under the old one. The fix is to stop deriving the directory name from the remote on every run: the store keeps an index from canonical project root to project id, consults it first, and mints a new id only when the root is unseen. The index is store metadata, not a snapshot: it is mutable by design, where snapshots are not, so it carries its own version and sits outside `SNAPSHOT_SCHEMA_VERSION`, which continues to govern only the immutable artifacts. Introducing it therefore does not bump the snapshot schema and does not make a v0.1 snapshot unreadable — which is the whole point, since those snapshots are what the index exists to adopt. The consequences are stated rather than discovered later: a project keeps one id for its lifetime regardless of remote changes; two clones of the same remote have different roots and therefore remain separate histories, which is correct, since they are different working copies; removing a remote changes nothing; and no snapshot is moved or rewritten, so immutability holds — only the index maps root to id. This also settles the linked-worktree transition introduced by the S5 decision, where the first unconsented run has no git-derived identity to offer.
    Histories that already exist are adopted rather than abandoned, which the forward-looking rule alone does not achieve: on the first v1.0 run in a project, if the root has no index entry but a store directory exists under the id v0.1 would have derived, the index is pointed at that directory and it remains canonical. Nothing is moved or rewritten, so immutability holds. Adoption is exclusive, which the rule needs because a v0.1 remote-derived id is *shared* by every clone of that remote: without exclusivity two clones would each adopt the same directory, contradicting the separation decided just above. The index therefore records the claiming root alongside the id, and a legacy directory is adopted only while unclaimed. A second clone finds it claimed by another root, starts its own history, and is told in a diagnostic that a shared legacy history exists and where — nothing is deleted or rewritten. First run claims it; that is arbitrary but deterministic, and stated here so it is not discovered. Where both a remote-derived and a path-derived directory exist for one root, the one named by the more recent `latest` is adopted and the other is reported by `pfl gc` as reclaimable.
  * **Interpretation reproducibility decided: interpretations are persisted and read back.** Today they are recomputed on every read with a fresh random id, and `CLASSIFIER_VERSION` is never stored, so snapshot immutability stops short of report output. In v1.0 `inspect` writes the interpretation into the `interpretations/` directory that already exists but has no writer, read commands use the stored one, and `Interpretation` gains the `schemaVersion` it currently lacks while being read through the versioned deserializer. A report therefore reproduces, and it can state which classifier produced it. Snapshots written before v1.0 carry no interpretation, and they stay readable: for those, the interpretation is recomputed as it is today, and the document records that it was recomputed and by which classifier version, so a consumer can tell a reproduced report from a recomputed one. That distinction needs somewhere to live rather than only being asserted, and it does not belong on the persisted type: a stored interpretation is always stored, so an `origin` field on `Interpretation` would have one reachable value. It is a property of the answer, not of the artifact. The read commands' `--json` `data` therefore reports `interpretation: { classifierVersion, origin }` with `origin` of `stored` or `recomputed`, and the terminal output says the same in one line when a report was recomputed. Absence of a stored interpretation is never an error.
  * **The three version knobs given a defined relationship**, settled before the freeze because each affects what a stored artifact means. `SNAPSHOT_SCHEMA_VERSION` governs on-disk readability alone: an unknown value is refused rather than guessed. `RESOLUTION_SEMANTICS_VERSION` feeds the resolved digest and is diff-visible, so the same harness resolved under different semantics is a different resolved snapshot. `CLASSIFIER_VERSION` feeds no digest — a classifier change does not invalidate a stored snapshot — but it is persisted with the interpretation, so a report can state which classifier produced it. The package version is independent of all three. The dead `interpretations/` storage and the missing `schemaVersion` on `Interpretation` are resolved as part of this, since persisting the classifier identity requires the artifact to be writable and versioned.
  * **Relation types reconciled.** Three of the seven declared types are emitted (`shadows`, `overrides`, `accumulates-with`); `contains`, `discovered-from`, `resolves-to`, and `applies-to` have no producer. All seven are settled in **one table** giving producer, meaning, fixture, and whether rendering and diff consume each — these are public schema decisions, not type-level tidying — and that table is the deliverable that separates this freeze from the implementation issues; then implement or withdraw, and de-duplicate the declaration currently maintained in both `core/resolved.ts` and `snapshot/store.ts`.

* **Acceptance Criteria — implementation delivered in this milestone.** These build against the decisions above and can be split into issues once those are settled.
  * **Consent enforced at a choke point covering every read path in the M6 inventory.** Moving the check into `walkHarnessPaths` / `isPathWithin` alone is insufficient: the pre-consent reads identified as S5 occur in `project-identity.ts` (`.git`, `gitdir:`, `commondir`, and ancestor traversal), which the walk layer never sees. Closed when a test asserts that each inventoried path is unreachable without a grant covering it. The boundary the inventory draws is stated rather than inferred: locating `.git` within the project root, and reading a `.git` directory's own config inside that root, are project-local and implicit; following a `gitdir:` that resolves outside the root, and walking above the root to find an ancestor `.git`, are out-of-project reads and are gated. That line is what makes the choke-point test's target set decidable.
  * `--snapshot latest` accepted by `diff`, which currently requires two explicit positional ids.
  * **Snapshot retention and garbage collection implemented against a stated policy.** Retention is by run count per project, not by age, so a rarely-inspected project keeps a usable history: **the twenty most recent runs are kept by default**, adjustable per invocation. The run named by `latest` is always retained, and a run is retained or reclaimed as a whole — the observed snapshot, its resolved counterpart, and its stored interpretation together — so collection cannot leave a resolved snapshot whose interpretation has been reclaimed, or an interpretation with nothing to interpret. For that to be mechanical rather than inferred, the interpretation id joins the observed and resolved ids in the `latest` pointer and in the stored run summary, which carry only the first two today. Collection is an explicit `pfl gc` command supporting `--dry-run` and `--keep <n>`, never a side effect of `inspect`, because deleting a user's records silently is out of character for a read-only tool; it exits 0 on success and 6 on store failure, and its `--json` document lists what was or would be reclaimed. An artifact that cannot be parsed is reported, not deleted. With the root index above, remote changes no longer orphan a directory at all; the residual case — a project whose root no longer exists on disk — is listed by `pfl gc` and reclaimed only under `--prune-orphans`, so unbounded growth has a remedy the user invokes rather than one that runs behind them.
  * Package `exports` explicitly restricted to block deep imports, enforcing the CLI/schema-only contract.
  * `ResolvedSnapshot` utilizes `deepFreeze`.
  * **The freeze has verifiable deliverables.** Adding an ADR does not demonstrate that a contract is frozen. The milestone closes on: a schema definition or schema fixture; golden files for a representative snapshot and for each command's JSON output; a read-compatibility test against the previous version; a documented schema-bump procedure with the rule separating breaking from non-breaking change; and an `ElementId` collision fixture.

### M9: OpenCode Adapter
* **Goal**: Introduce the third runtime adapter securely. The discovery and resolution core is already adapter-agnostic at the I/O layer, but not at the semantic layer; that has to change before a third adapter arrives rather than after.
* **Acceptance Criteria**:
  * Shared runtime adapter scaffolding extracted first. Roughly 60% of each existing adapter is mechanical duplication — `symlinkElement`, `unsupportedElement`, `unreadableElement`, `toObservedProject`, `metadataForPath`, `readTextOrNull`, and `isRecord` are byte-identical across the two — so extraction removes the duplication that made S1 a two-place fix in the first place. The claim is about what comes after, not about S1 itself: S1 is repaired in M6 against both existing adapters, and the extraction here folds those repairs into one place so the next adapter inherits them instead of reimplementing them.
  * The semantic layer opened to adapters. `FACETS_BY_KIND` is a module-private, core-owned table keyed by element kind with no registration hook, so any adapter introducing a new kind must edit `src/classify/` and bump `CLASSIFIER_VERSION`. The coupling already leaks: Claude Code's `plugin` and Codex's `fallback-instructions` are emitted by adapters, absent from the table, and silently classified as unknown.
  * `findings.ts` no longer keyed on hardcoded kind spellings, which currently cause a rule to silently never fire when an adapter spells a kind differently.
  * `NativeOrigin` and the origin render order in `cli/graph-model.ts` and `cli/list.ts` able to accommodate OpenCode's scope model. Any change to `NativeOrigin` itself is a schema change and therefore lands in M8 under its entry condition, not here; this milestone consumes the frozen schema rather than altering it.
  * Adapter registration unified. `ADAPTERS`, `CONSENT`, and `RUNTIME_NAMES` are three parallel hand-maintained records keyed by the same string with no type linking them; omitting one surfaces only at runtime. The unified registry and any facet-registration hook stay internal: neither appears in `package.json` `exports`, so the CLI-and-schema-only contract is preserved.
  * OpenCode adapter implemented against the scope, origin, and path model documented in M8. This milestone is implementation only: the investigation that produced that model is an M8 deliverable, because the freeze depends on it.
  * **OpenCode's read paths added to the M6 inventory, and the M8 choke-point test re-run over the extended inventory.** The test is parameterised by the inventory rather than written against its M6 contents, so "no inventoried path is reachable without a grant covering it" keeps holding as adapters are added. Without this the guarantee would be true only of the two adapters that existed when it was written.
  * Mandatory pre-merge security review conducted and recorded under `docs/security/reviews/`, per §3.3. A new adapter is a new read surface; the consent choke point delivered in M8 is what makes that surface reviewable by construction rather than by per-adapter trust.

### M10: v1.0 Release Preparation
* **Goal**: Finalize governance, platform support, and stability guarantees.
* **Acceptance Criteria**:
  * `LICENSE`, `CHANGELOG.md`, and `CONTRIBUTING.md` published. The package already declares `"license": "MIT"` while no licence file exists in the repository or the tarball.
  * `.github/ISSUE_TEMPLATE/` and `CODEOWNERS` added.
  * macOS runners added to CI. The matrix is currently Ubuntu-only, and the managed-scope discovery introduced in M7 is macOS-specific, so it cannot be exercised on Linux runners alone.
  * POSIX exclusivity documented in `README.md` and in the `package.json` `os` field.
  * Semver policy, CLI stability, and schema compatibility guarantees documented, including the distinction between the package version and `SNAPSHOT_SCHEMA_VERSION`. ADR 0001 defines that distinction, but it is not surfaced to users anywhere.
  * Coverage measurement added. No coverage tooling, CI step, or reporting exists today, so the untested modules — `cli/graph-model.ts`, `cli/read.ts`, and both `runtime/*/paths.ts` search-area tables — are identifiable only by file absence.
  * The release workflow exercised before v1.0 in two stages, because provenance cannot be observed without publishing. First, a release-candidate tag runs the full workflow with `npm publish --dry-run`, confirming tag/version agreement, the tarball smoke test, and that the workflow's permission block is configured as trusted publishing requires. The OIDC token exchange and provenance attachment are not exercised by a dry run and are confirmed only by the real publish. Then the v1.0 publish itself is the first real run, after which provenance is checked on the published artifact.
  * The npm version required for trusted publishing **asserted inside the workflow** — failing early with a clear message when the runner's npm is too old — rather than pinned, which would fight the toolchain the runner ships, and rather than documented only in the README.
  * Source map publication resolved. Maps are emitted, but `files: ["dist"]` excludes `src`, so they resolve to nothing in the published package. **Decision: the maps stop being emitted for the published build.** Shipping `src` to make them resolve would enlarge the package for a benefit that a source checkout already provides. The accepted cost is that stack traces from the published package point at compiled positions.
  * NPM provenance confirmed on the published v1.0 artifact (the second stage above). The workflow already grants `id-token: write` and publishes through npm trusted publishing, which attaches provenance without an explicit flag, so the outstanding work is verification rather than enablement.
